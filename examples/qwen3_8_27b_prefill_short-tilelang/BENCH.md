Batch 1, no history, prompt lengths 128 / 256 / 512 / 1024, prefill up to the first
token. Backend: tilelang 0.1.15 kernels, called from the runtime module
`runtime/twin.py` (the twin of `model.py`). Reference implementation for speed:
SGLang 0.5.21 in `./sglang-env` (measured by me, same card, same session).

## 2. Every timed iteration really recomputed (assertions, not samples)

- SGLang: per iteration `extend_prefix_lens == [0]`, `extend_seq_lens == [T]`,
  positions `0..T-1`; the K/V slots of all 16 attention layers and the request's
  GDN state slot are set to NaN before the forward and asserted NaN-free and
  non-zero after; outputs agree with warm-up 0; a stubbed forward makes the
  assertion fail (negative control). Radix cache off, new request every iteration.
- Mine: before every iteration (after the first) every static buffer of the
  length's engine (hidden ping-pong, norm outputs, projections, q/k/v/g/beta,
  attention q, mixer output, MLP activation, K/V caches, conv windows, recurrent
  states, last-row norm, logits) is filled with NaN and asserted NaN; after the
  call the logits and all four cache outputs must be finite and bitwise equal to
  the first iteration's, argmax equal. A replay that skipped any kernel would leave
  NaN behind. Every per-iteration assertion record is in the run's JSON.

## 3. Warm-up and sampling rules

One driver (`bench/alternate.py`) starts both workers on the same physical card in
the same session, loads both, then for each length runs R = 6 rounds; in each round
both workers are benched back to back (order alternates between rounds), each call =
3 untimed warm-up prefills + 10 timed prefills. The number reported for a length and
a side is the median of all 60 timed iterations; the range is their min and max.
The SM clock is read before and after each call and after every timed iteration; the
other compute processes on the card are recorded before each call.
Card choice: GPU 1. GPU 0 idles at 70 C / 134 W with an `nvidia-cuda-mps-server`
resident (not started by this work); a whole-forward run there gave the T=1024 rows
4-13 % slower with a wide range (WORKLOG, segmentation entry); GPU 1 idles at 30 C.

## 5. Regime: where memory-bound turns compute-bound

**By hand.** A bf16 weight GEMM does 2·T·N·K FLOP on 2·N·K bytes of weight: T FLOP
per byte. The H200 ridge is 989.5 / 4.8 = 206 FLOP/B, so every large linear is
memory-bound at T = 128 and compute-bound from T = 256 on; for the whole forward
the switch is at 10.71 ms / (6.36 ms / 128) = 216 tokens. At the 1500 MHz clock
actually used the ridge is 811 / 4.8 = 169 tokens.

**analyze, side by side** (`reports/analyze/current/SUMMARY.md`, `tilefoundry analyze
--roofline --dim seq_len=T` per selection). Per matmul analyze and the hand count
agree: w_gate is 38.3 us memory-bound at 128 and 46.1 us compute-bound at 256
(hand: 37.1 us of weight at 4.8 TB/s; 2·256·17408·5120 / 989.5e12 = 46.1 us). Per
layer they do not agree: analyze calls the GDN layer memory-bound at all four
lengths and composes the forward to 17.24 / 23.93 / 38.99 / 69.99 ms against the
ledger's 10.71 / 12.73 / 25.47 / 51.05 ms. Neither number is wrong for its program:
analyze prices the authored HIR as written -- every op's result through HBM (86.4 GB
at T=128 against 51.4 GB compulsory, 352 GB at T=1024) and the delta rule in f32 --
the ledger prices compulsory traffic on bf16 tensor cores, which is what a fused
implementation can reach. FLOPs agree (analyze 6243.5 bf16 + 58.1 f32 GFLOP vs
ledger 6294.0 at T=128). The gap between the two is what fusion has to recover
(section 8).

**Measured.** Whole forward (final table): doubling T from 128 to 256 costs only
x1.35 in time, 256 -> 512 x1.67, 512 -> 1024 x1.88: the weight-streaming floor is
still visible at 256 and the time becomes proportional to the work only from 512.
The switch is therefore not sharp at 206 tokens: it spans 128..512. Per GEMM
(gdn_in, N = 16640, `reports/plan_gemm_time.json`): 46.3 / 63.5 / 121.6 / 245.3 us;
the memory floor is 35.5 us at every T, the compute floor (811 TF) 26.9 / 53.8 /
107.6 / 215.1 us: T = 128 runs at 1.30x the memory floor (3.7 TB/s), T >= 256 at
1.18x / 1.13x / 1.14x the compute floor at the clock used.

## 7. Decision 1 — segmentation

**Decision.** One kernel graph for all four lengths, with one fork in it: the N = 5120
projections run split-K 2 (a GEMM writing two f32 partial planes + a reduce kernel
that adds the residual and lands bf16) where the unsplit GEMM cannot fill the 132 SMs:
o_proj and down at T=128, down at T=256 (plan v3; o_proj at T=256 is unsplit with
80-wide tiles, 35.6 vs 37.7 us split); at T >= 512 each is one GEMM with the residual
added in its epilogue. Inside that graph
every length has its own tile plan (`runtime/plan.py`): four GEMM plans, four
attention-core configurations, per-length RMSNorm rows per CTA. Layer kernels:

    GDN layer:       rmsnorm -> gdn_in GEMM [qkv|z|b|a] -> b|a split-K GEMM + reduce (overwrites b|a) -> gdn_prep
                     -> gdn_chunk -> gdn_scan -> gdn_gated_norm
                     -> o_proj(+residual) -> rmsnorm -> gate_up(+SwiGLU) -> down(+residual)
    attention layer: rmsnorm -> att_in GEMM [q+gate|k|v] -> attn_prep -> attn_core(+sigmoid gate)
                     -> o_proj(+residual) -> rmsnorm -> gate_up(+SwiGLU) -> down(+residual)
    (T=128: o_proj and down, T=256: down = split-K GEMM + reduce kernel)

**What was tried, whole forward** (plan v2, before the SOL pass; `runtime/experiments/segment_xplan.py`,
`reports/segment_xplan_gpu1.json`, GPU 1, 1500 MHz, median of 20, ms). Each row is a
prompt length, each column the plan that serves it -- one shared plan for all
lengths is one column:

| T \ plan of | 128 | 256 | 512 | 1024 |
|---:|---:|---:|---:|---:|
| 128 | **19.03** | 22.09 | 25.59 | 27.28 |
| 256 | 32.79 | **25.81** | 29.14 | 31.19 |
| 512 | 57.02 | 46.93 | **43.47** | 44.40 |
| 1024 | 108.92 | 90.65 | 84.00 | **81.79** |

The best single shared plan (512's) loses 34 % at T=128 and 13 % at T=256; every
length is fastest with its own plan. The split-K fork: plan 256 (split-K) at T=512 is
+8.0 % (46.93 vs 43.47); plan 512 (no split) at T=256 is +12.9 % (29.14 vs 25.81).
Per GEMM (sweeps, `reports/sweep_gemm_T*.json`, us): best split-K 2 vs best unsplit
-- T=128 o_proj 27.83 vs 30.38, down 59.71 vs 79.59; T=256 o_proj 40.44 vs 45.40,
down 90.61 vs 109.83. Split 4 and 8 were worse at T=128 (o_proj 31.75 / 38.91).

**Why the fork is between 256 and 512.** N = 5120 with 160-wide tiles is 32 N tiles;
with 128-row M tiles that is 32 / 64 / 128 / 256 CTAs at T = 128 / 256 / 512 / 1024
on 132 SMs. Below 512 the unsplit GEMM leaves more than half the SMs idle, and
split-K 2 doubles the CTAs for the price of 2 x T x 5120 x 4 B of f32 partials
written and read again (10.5 MB each way at T=256) and one more kernel; at T = 512 one wave is already
full (128 CTAs), so splitting only adds the traffic and the kernel.

## 9. Decision 3 — which dimensions each operator supports

Supported prompt lengths: exactly 128, 256, 512, 1024 (`plan.for_length` refuses any
other; `run.py --prompt-tokens` picks one). Every kernel is compiled with T as a
static constant.

- **GEMMs: one kernel per (linear, length).** A dynamic-M kernel costs nothing and
  gains nothing (gdn_in, same config: dynamic vs static M 62.4 vs 62.3 us at M=128,
  64.6 / 64.7 at 256, 122.5 / 122.4 at 512, 240.7 / 240.7 at 1024,
  `runtime/experiments/gemm_dynM.py`); what differs per length is the tile config:
  the T >= 256 config at M = 128 is +35 % (62.4 vs 46.3 us). Padding a 128-token
  prompt into the 256-row GEMM costs only +4 % for that GEMM (64.7 vs 62.4 us,
  memory-bound), but padding the whole forward to the next length costs +35.6 %
  (128 -> 256: 25.80 vs 19.03 ms), +68.1 % (256 -> 512: 43.39 vs 25.81), +88.1 %
  (512 -> 1024: 81.77 vs 43.47): attention, GDN, norms and the compute-bound GEMMs
  all pay for the padding rows. One implementation fewer saves only compile time and
  the length's static buffers (0.21 GB at T=128, 0.48 GB at T=1024, measured as
  allocated memory of one engine) -> no length shares another's implementation.
  Configs (`runtime/plan.py` v3, section 12): tile widths chosen so the CTA count fills
  whole waves of the 132 SMs. gate/up half-tile HB: 144 at T=128 (121 CTAs, BK 128 x 2
  stages), 144 at 256 (242 CTAs), 176 at 512 / 1024 (396 / 792 CTAs = 3.0 / 6.0 waves);
  T=128 o_proj/down BN 80 split 2 (128 CTAs), gdn_in / att_in BN 128 (130 / 112
  CTAs); T>=256 gdn_in BN 256 (65 x 256 = 16640 padded rows), att_in 224, o_proj/down
  160 (32 N tiles; 128 / 256 CTAs at 512 / 1024). Where measured >= 1 % faster and
  bitwise equal, a hand warp-specialized kernel (`runtime/kernels/gemm_ws.py`,
  `plan.ws_choice`) serves the linear instead: persistent 132-CTA kernels for all five
  linears at T=1024 and gdn_in / gate_up at 512, packed-epilogue o_proj at 512,
  gate_up at 256.
- **Attention core: one configuration per length** (`attention.CORE_CONFIG`; core us
  per T = 128 / 256 / 512 / 1024 from the variants table in ATTENTION_NOTES.md):
  T=128 1 head/CTA + early gate + output dims split over 2 CTAs (10.0; without the
  split 12.4); T=256 1 head/CTA + early gate (16.0; DSPLIT 2 17.0); T=512 1 head/CTA +
  late gate (26.3; early 26.8-27.1); T=1024 2 heads/CTA (two consumer warpgroups share
  K/V) + late gate (45.2; 1 head/CTA 55.7). Reason: at 128-256 the core is latency
  bound (48-96 CTAs), more CTAs win; at 1024 halving the K/V traffic from L2 wins.
- **GDN: one source, compiled per length** (T multiple of 64); gdn_prep rows per
  warp R = 2 for T <= 256, 4 above; gdn_chunk grid (T/64, 48); gdn_scan two CTAs per
  value head at every length (each CTA owns 64 of the 128 value columns, no data
  between them); gdn_gated_norm per length.
- **RMSNorm: one source, rows per CTA per length** 1 / 2 / 4 / 4 (us at T = 128:
  rows 1/2/4/8 = 3.30 / 3.60 / 3.72 / 5.65; at 1024: 6.19 / 6.29 / 5.96 / 6.13). The
  kernel sums in torch's order so it is bitwise equal to the HIR (section 6).
- **GDN b|a projections: one kernel per length**, split count fixed by correctness
  (cuBLAS's own choice for N=48: 8 slices for T <= 512, 4 at T=1024, section 6), tile
  width by time (bitwise the same output for every width): us per call at T = 128 /
  256 / 512 / 1024 for BN 16: 4.83 / 5.28 / 9.00 / 14.69, BN 32: 5.54 / 5.82 / 5.99 /
  8.96, BN 48: 6.06 / 6.13 / 6.20 / 9.34, BN 96: 7.62 / 7.71 / 7.79 / 11.69 -> BN 16
  for T <= 256, 32 above.
- **Length-independent:** final norm (one row) and lm_head GEMV are one kernel for
  all lengths; embedding gather per length.

## 10. Artifact chain

Every row: the part of `model.py` it implements -> its scheduled HIR -> the TIR
`tilefoundry schedule finalize` wrote from that file -> the tilelang kernel that runs
it -> the lengths it serves. Generated from the files on disk by
`tools/chain_table.py` (a row is printed only if both files exist). Generators:
`tools/gen_scheduled.py` (GEMMs), `tools/gen_scheduled_small.py`,
`tools/gen_scheduled_attention.py`, `tools/gen_scheduled_gdn.py`. Every scheduled
file names its runtime kernel and lists in its header where it differs from the kernel.
The evaluator cannot run scheduled HIR (`MeshCoord is not modelled`), so the
scheduled -> TIR link is `finalize` (verified TIR) and the kernel -> `model.py` link is
the twin `check` (section 6).

**Implementation sets -> lengths -> TIR.** Four sets, one per length; each set is
the same kernel graph (section 7) with its own compiled kernels. Two kernels are
shared by all four sets.

| set | serves T | its TIR files (finalized from the scheduled HIR of the same name under `scheduled/`) |
|---|---|---|
| T128 | 128 | `tir/gemm/{gdn_in,att_in,gate_up,o_proj,down}_T128.py`, `tir/gemm/gdn_ba_T128.py`, `tir/small/{rmsnorm,embed,reduce_sk2,reduce_ba}_T128.py`, `tir/attention/attn_{prep,core}_T128.py`, `tir/gdn/gdn_{prep,chunk,scan,norm}_T128.py` |
| T256 | 256 | the same names with `_T256` (includes `reduce_sk2_T256`: split-K set) |
| T512 | 512 | the same names with `_T512`, no `reduce_sk2` (o_proj/down are residual-epilogue GEMMs) |
| T1024 | 1024 | the same names with `_T1024`, no `reduce_sk2` |
| shared | all | `tir/small/rmsnorm_last.py` (final norm, last row), `tir/small/lm_head.py` (GEMV) |

The GDN scan: the kernel runs each value head on a 2-CTA cluster, each CTA owning 64
of the 128 value columns; `scheduled/gdn/gdn_scan_T*.py` states that split with no
cross-CTA data (each CTA writes only its own columns). The gated RMSNorm, which needs
both halves, is its own kernel (`gdn_gated_norm`) with its own scheduled HIR
(`scheduled/gdn/gdn_norm_T*.py`); an earlier fused form could not state the pair's
row-sum exchange (section 8). No finalized TIR in this project carries an explicit
synchronization statement; inside a CTA the order follows the region structure.

## 11. Where the time goes, and the gap to the lower bound

Per-kernel GPU time of one forward (`runtime/profile_forward.py`, GPU 1,
`reports/profile/final_T*.txt`), ms:

| T | all kernels | GEMMs (+split-K reduce) | of which gate/up (SwiGLU) | GDN b|a split-K + reduce | GDN prep+chunk+scan+gated norm | attention prep+core | rmsnorm (incl. last row) | lm_head |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 128 | 19.54 | 16.44 | 7.93 | 0.39 | 1.42 | 0.16 | 0.56 | 0.57 |
| 256 | 26.35 | 22.43 | 10.46 | 0.41 | 2.08 | 0.27 | 0.58 | 0.57 |
| 512 | 44.16 | 38.62 | 19.49 | 0.44 | 3.36 | 0.48 | 0.68 | 0.57 |
| 1024 | 82.87 | 73.67 | 35.89 | 0.68 | 5.96 | 1.09 | 0.89 | 0.56 |

- T = 128 (memory-bound): the GEMMs stream 48.7 GB of decoder weights in 16.4 ms =
  3.0 TB/s against 4.8 (the GEMV for lm_head reaches 4.44 TB/s). Gate/up is 123 us per
  call against 74 us at 4.8 TB/s. This is the main gap to the 10.71 ms bound
  (19.57 ms measured, 1.83x).
- T >= 256 (compute-bound): GEMM work is 2·T·24.35 GFLOP; at T = 1024 the GEMMs run
  at 677 TFLOP/s = 83 % of the 811 TFLOP/s bf16 peak at the 1500 MHz clock used
  (gate/up 651 TFLOP/s). Measured / bound = 2.07x / 1.73x / 1.62x at 256 / 512 / 1024,
  of which 1.22x is the clock (989.5 TF assumes 1.83 GHz, the run used 1.5 GHz).
- Everything that is not a GEMM is 3.1 ms (T=128) to 9.2 ms (T=1024); the b|a split-K step
  (kept for exact agreement with the reference, section 6) is 0.39 to 0.68 ms of it.
